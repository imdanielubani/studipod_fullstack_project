# Backend API integration

> **Status:** structure only. No API client or endpoint calls exist yet. Endpoints are taken
> from the backend's OpenAPI document as each backend module ships; none are invented in
> the webapp.

## Configuration

| Variable                  | Example (production)              | Used for                         |
| ------------------------- | --------------------------------- | -------------------------------- |
| `NEXT_PUBLIC_API_URL`     | `https://api.studipod.com/api/v1` | Base of every REST request       |
| `NEXT_PUBLIC_WS_URL`      | `wss://ws.studipod.com`           | Socket.IO connection             |
| `NEXT_PUBLIC_LIVEKIT_URL` | `wss://<project>.livekit.cloud`   | LiveKit room connection          |
| `NEXT_PUBLIC_APP_URL`     | `https://app.studipod.com`        | Absolute links, redirect targets |

Values are read through `src/config/env.ts`, which validates them with Zod. The backend must
list `NEXT_PUBLIC_APP_URL` in `CORS_ALLOWED_ORIGINS` (credentials enabled) and use it as
`WEBAPP_URL` for links in emails.

## Backend contract the client relies on

- Candidate routes live directly under the API base (`<API_URL>/...`); admin routes
  (`/admin`) are never called by the webapp.
- Success: `{ "data": ... }`; collections add `meta` (cursor pagination: `limit`,
  `nextCursor`, `hasMore`).
- Error: `{ "error": { "code", "message", "details", "requestId" } }`. The client branches on
  `code`, never on `message`.
- IDs are UUIDv7 strings; timestamps are ISO 8601 UTC; JSON fields are camelCase.
- `POST` requests that create bookings or payments send an `Idempotency-Key` header.
- Breaking changes ship as `/api/v2`.

## Planned client layers

```text
lib/api/http-client.ts      openapi-fetch client over native fetch: base URL,
                            credentials, Authorization header, X-Request-Id,
                            timeout (AbortController), typed ApiError,
                            single-flight refresh on 401
lib/api/query-client.ts     TanStack Query defaults (exists)
lib/socket/socket-client.ts Socket.IO client: token in handshake `auth`, reconnect
                            and re-authenticate after refresh
types/generated/            output of `pnpm api:generate` (never edited by hand)
features/<f>/api/
  ├── keys.ts               query-key factory
  ├── requests.ts           typed request functions (one per endpoint)
  └── queries.ts            useQuery / useMutation hooks
```

**Why `openapi-fetch`:** it is a thin (about 6 kB) typed wrapper over native `fetch` whose
paths, parameters and responses are checked against the generated OpenAPI types, so a
backend contract change becomes a type error instead of a runtime bug. No other HTTP client
(axios and similar) is used.

Responses that drive security-relevant UI (current user, subscription entitlements) are also
parsed with Zod at runtime.

### Generating types

```bash
pnpm api:generate http://localhost:3000/<openapi-json-path>   # or a local schema file
```

The JSON path is defined by the backend's Swagger set-up (served alongside the `/api/docs`
UI when `SWAGGER_ENABLED=true`). Output: `src/types/generated/api-schema.d.ts`, committed so
builds do not depend on a running backend.

## Real-time (Socket.IO)

- Connect only after sign-in, with the access token in the handshake `auth` payload (never
  in the query string).
- On token refresh, re-authenticate the socket; on sign-out, disconnect.
- Events update the TanStack Query cache; after a reconnect, invalidate affected queries
  because events may have been missed.
- When offline, show the connection state and disable sending; do not queue messages.

## File uploads

1. Ask the backend for a presigned upload URL (it validates content type and size;
   default limit 10 MiB, URL valid for about 5 minutes).
2. `PUT` the file directly to Cloudflare R2 with the returned URL and headers.
3. Tell the backend the upload is complete; it verifies, scans and re-encodes the file.
4. Private files are downloaded only through short-lived presigned `GET` URLs from the API.

The webapp never holds storage credentials, and files never pass through the Next.js server.
The R2 upload origin must be allowed in `connect-src` when the CSP is completed.

## Payments and subscriptions

- Checkout uses Stripe Checkout and changes use the Stripe customer portal. The backend
  creates the session and returns a URL; the webapp redirects to it.
- No Stripe secret key, and no card data, ever exists in the webapp. Entitlements come from
  the backend (mirrored from Stripe webhooks), never from the redirect result.

## Video sessions (LiveKit)

1. The candidate opens a confirmed booking.
2. The webapp asks the backend for a LiveKit access token for that session. The backend
   checks participation and the session window, then issues a short-lived token.
3. The webapp connects to `NEXT_PUBLIC_LIVEKIT_URL` with that token using
   `@livekit/components-react`. Camera and microphone permission is requested only at
   this point (`Permissions-Policy` allows them for this origin only).

LiveKit API keys and secrets exist only in the backend. Video components are loaded with
dynamic imports so the LiveKit bundle is not part of other pages.

## Error handling

| Condition             | Client behaviour                                                      |
| --------------------- | --------------------------------------------------------------------- |
| Offline               | Do not send; show the offline notice; queries resume when back online |
| Network error/timeout | Retry with backoff (queries only), then error state with retry        |
| `400` / `422`         | Map `details[].field` onto form fields                                |
| `401`                 | Single-flight refresh, retry once, otherwise sign out                 |
| `403`                 | Forbidden screen or inline notice (for example, plan required)        |
| `404`                 | Not-found state for the resource                                      |
| `409`                 | Conflict message from `code` (for example, slot no longer available)  |
| `429`                 | "Too many requests"; respect `Retry-After`                            |
| `5xx`                 | Generic error showing the `requestId` for support                     |

## Adding an integration (checklist)

1. Confirm the endpoint exists in the backend OpenAPI document and regenerate types.
2. Add the request function, query keys and hooks in the feature's `api/` folder.
3. Handle loading, empty, error, offline and success states in the UI.
4. Add tests, and a Playwright journey for critical flows.
