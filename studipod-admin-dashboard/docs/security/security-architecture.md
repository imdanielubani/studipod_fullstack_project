# Security architecture

The dashboard is an internal console with access to candidate personal data, payments
and moderation tools. Its security model has three independent layers:

1. **Cloudflare Access** in front of `stuadminapp.studipod.com` (network/identity gate).
2. **Application authentication** in the dashboard (see
   [authentication and session](authentication-and-session.md)).
3. **Backend authorisation** on every API request (authoritative).

Any one layer failing must not grant access on its own. Cloudflare Access never replaces
application sign-in, and dashboard permission checks never replace backend authorisation.

## Secrets and environment variables

- The dashboard holds **no backend secrets**: no JWT secrets, database URLs, payment
  gateway keys, email provider keys or service-account files. They belong to
  `studipod-backend`.
- Only `NEXT_PUBLIC_*` variables reach the browser, and they are inlined at build time.
  They contain public URLs only. See [environment variables](../deployment/environment-variables.md).
- Real `.env*` files are git-ignored and docker-ignored; only `*.example` templates are
  tracked.
- No credentials are hard-coded, including test credentials. End-to-end tests read them
  from CI secrets when they are added.

## Browser storage

| Data                                        | Allowed storage                                   |
| ------------------------------------------- | ------------------------------------------------- |
| Access token                                | Memory only                                       |
| Refresh token                               | `HttpOnly; Secure; SameSite=Strict` cookie        |
| Admin data (users, payments, messages)      | TanStack Query memory cache, cleared on sign-out  |
| UI preferences (column visibility, density) | `localStorage` is acceptable; never personal data |

## HTTP security headers

Set for every response in `next.config.ts`:

| Header                      | Value                                                                            |
| --------------------------- | -------------------------------------------------------------------------------- |
| `Content-Security-Policy`   | `frame-ancestors 'none'; base-uri 'self'; form-action 'self'; object-src 'none'` |
| `X-Frame-Options`           | `DENY`                                                                           |
| `X-Content-Type-Options`    | `nosniff`                                                                        |
| `Referrer-Policy`           | `strict-origin-when-cross-origin`                                                |
| `Permissions-Policy`        | camera, microphone, geolocation and payment disabled                             |
| `Strict-Transport-Security` | `max-age=63072000; includeSubDomains`                                            |
| `X-Robots-Tag`              | `noindex, nofollow, noarchive`                                                   |

`X-Powered-By` is disabled.

**Planned with authentication:** a full CSP generated per request in `src/proxy.ts` with a
nonce for `script-src`, `connect-src` limited to the app, API and WebSocket origins, and
`img-src` limited to the app and the media storage origin.

> If a future feature (for example, video session review) needs camera or microphone
> access, relax `Permissions-Policy` for that route only.

## Input, output and XSS

- All form input is validated with Zod schemas (shape only; the backend re-validates).
- User-generated content (messages, reports, profile text) is rendered as text through
  React. `dangerouslySetInnerHTML` is not used; if rich text is ever required, it is
  sanitised with a maintained sanitiser and an allowlist.
- Redirect targets after sign-in accept only same-origin relative paths.
- Data exports are generated by the backend; the dashboard does not assemble CSV from
  sensitive data client-side.

## CSRF

The access token is sent in the `Authorization` header, which browsers never attach
automatically, so admin API calls are not CSRF-prone. The refresh cookie is
`SameSite=Strict` and path-scoped to auth routes; the backend additionally checks `Origin`
against its CORS allowlist on refresh and logout.

## Dependencies and supply chain

- Exact versions are pinned in `package.json`; installs use `--frozen-lockfile`.
- `pnpm-workspace.yaml` blocks dependency install scripts except a reviewed allowlist.
- `pnpm audit --audit-level=high` runs in CI.
- The Docker image runs as the unprivileged `node` user, with a read-only root filesystem
  where the platform allows it.

## Logging

- No `console.log` in committed code (ESLint warns). Client errors are reported without
  tokens, passwords, codes or personal data.
- Error boundaries show a reference (`digest`) instead of stack traces.
